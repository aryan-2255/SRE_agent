What it does

The 3 AM problem

When production breaks at night, someone gets woken up, reads logs half asleep, guesses a cause, and changes things under pressure. NightShift does the first hour of that work: it notices the problem, reads the logs, traces and recent code changes, proves what went wrong, and prepares the fix. It never changes production on its own. Every risky step waits for a person to say yes on Jira or on the dashboard.

It is built on TrueForge, TrueFoundry’s open-source agent harness, unmodified. Each agent is a saved TrueForge agent with its own model, tools and approval list. TrueForge runs them, pauses them for approvals, runs their code in a Daytona sandbox, and records every step.

The system it protects today is the OpenTelemetry Astronomy Shop: a real online shop of 31 Docker containers in many languages, with live traffic. Nothing in the agents is specific to this shop. A different system needs a different onboarding file, not different agents.

When the agents wake up

One bad minute is not an incident

What the watcher checks verified live

  • Error % and requests per second of every watched service, from Prometheus, every 5 seconds.
  • Each service has its own limit. The shop’s AI assistant normally fails 17% of the time, so its limit is 35%, not 5%.
  • A synthetic customer adds 5 items to a cart every 30 seconds and checks the cart really holds 5. That catches bugs that return “success” with the wrong answer.

Noise guards

  • Minimum traffic, so 1 failure in 2 requests is not “50%”.
  • If a service it depends on is failing too, the incident opens on that service, and the other is listed as a symptom.
  • The same service cannot open a new incident for 10 minutes.
The supervisor

An AI decides the next step. Code decides what is allowed.

There is no fixed pipeline. After every agent finishes, the supervisor reads what every agent has said so far and picks one move. Code then checks that move against rules it cannot break. The supervisor brings judgment; the rules bring safety.

MoveWhen the supervisor uses it
runStart the next agent along the normal path.
askAn answer is weak or contradicts another; put a specific question to the agent that gave it.
send_backReturn work with concrete feedback: the reviewer rejects a fix, or the sandbox could not reproduce the cause.
escalateStop and hand over to a person, with the reason: external cause, conflicting evidence, limits reached.
finishOnly after the service is verified as recovered.

Rules the supervisor cannot break

  • Planning needs a proven cause (a sandbox reproduction), unless the cause is a flag, config or capacity.
  • CI/CD needs passing tests and a reviewer’s approval of the latest fix.
  • Each agent has a run limit (diagnosis 3, mitigation 3, fix 3…); 24 steps in total.
  • A cost cap per incident; over it, escalate.
  • Human approval is enforced by TrueForge on every changing tool, whatever the supervisor decides.
Agents talking

They question each other and send work back

An agent can be wrong. When one agent’s answer undermines another’s, the supervisor routes the disagreement to the agent that can resolve it, with the reason attached. These are the three conversations built into NightShift. built, not yet seen live: the flag incident above never needed them.

Tools and connectors

What the agents can touch

nightshift-ops verified live

Our MCP server, the only way into the running system. 19 tools, bearer token, every output masked for emails, card numbers and secrets.

Read: get_error_rates query_logs get_traces get_trace get_metrics get_recent_deploys get_flags list_services run_sql_readonly synthetic_check

Change (always paused): rollback deploy deploy_canary promote_canary restart_service scale_service set_flag · plus abort_canary, notify

TrueForge connectors connected

GitHub (token for the shop’s repo only): read commits and files, create branches, push, open and review PRs, merge.

Jira (Atlassian login): read and write issues. NightShift’s own approval bridge also uses Jira’s API to read /approve comments every 5 seconds.

Built into TrueForge

Daytona sandbox: agents run code there. Tested: it clones the repo, installs Node 24 and runs npm ci for the payment service.

Sub-agents, tool search, approval pauses, sessions with every step and its cost.

Any system: one onboarding file

The agents only know capabilities, such as “read logs” or “roll back”. The onboarding file says where each capability lives for this system. Adapters in nightshift-ops do the rest: Prometheus, OpenSearch, Jaeger, Docker Compose and flagd today. A system on CloudWatch, Datadog, Vercel or Render needs a new adapter, and the agents stay the same.

Platforms that ship their own MCP server (Supabase, Sentry, GitHub, Jira) are connected directly in TrueForge instead.

# nightshift/systems/astronomy-shop.yaml (trimmed)
name: astronomy-shop
repo:
  url: github.com/aryan-2255/opentelemetry-demo
runtime: { type: docker-compose }
telemetry:
  metrics: { type: prometheus }
  logs:    { type: opensearch }
  traces:  { type: jaeger }
services:
  payment:  { language: javascript,
              slo: { max_error_pct: 5 } }
  checkout: { depends_on: [payment, cart] }
  agent:    { slo: { max_error_pct: 35 } }
watch: { for: 2m, demo_for: 30s }
autonomy:
  auto: [notify]
  ask:  [rollback, set_flag, deploy, …]
  never: [drop_table, delete_data]
Safety and approvals

How a change gets approved

Nothing changes without a person

  • Changing tools are listed by name in each agent’s approval list. We never rely on a server’s “destructive” label alone.
  • Only team notifications are approved automatically.

Least access

  • The database tool accepts one SELECT, through a read-only role.
  • The GitHub token reaches only the shop’s repo.
  • Agents never see secrets; the sandbox never holds any.

Limits and a record

  • Run limits per agent, 24 steps and a cost cap per incident, then escalate.
  • Every tool call is recorded in TrueForge sessions and on the dashboard timeline.

The operations room

The dashboard judges watch

The dashboard at localhost:8090 is a live map, not a progress bar. The supervisor sits in the centre with the agents around it and the systems they reach on the outside. Each decision pulses from the supervisor to the agent it chose. Each tool call flashes a line to the system it touched. Questions and send-backs draw a line straight between two agents.

Around the map: every watched service with its live error rate and trend; the approval card with Approve and Deny; the agents’ conversation, quoting each decision and its reason; the exact log lines, traces and numbers the agents read; and a timeline of the whole incident with approval waits highlighted. Any past incident can be replayed at speed.

Hackathon rules

The three requirements, and where to see them

Reaches a real system

A live shop with real traffic

Agents read the shop’s Prometheus, OpenSearch and Jaeger data and change it through nightshift-ops; they also use GitHub and Jira. See the evidence panel and TrueForge sessions.

Runs code in a sandbox

Proof before a fix

Validation, coder and tester clone the repo into a Daytona sandbox and run tests they wrote. The sandbox setup is tested; the full code path is built, not yet run live.

Stops before irreversible actions

TrueForge pauses, a person decides

Every changing tool waits for Approve on the dashboard or /approve on Jira. verified live on INC-001.

Run it

Two repos, four commands

git clone --recursive https://github.com/aryan-2255/SRE_agent.git truforge_hackthon
cd truforge_hackthon/nightshift
./scripts/bootstrap.sh
./scripts/start-trueforge.sh
./.venv/bin/uvicorn control.app:app --port 8090

# break something and watch
./.venv/bin/python scripts/mcp_call.py set_flag \
  '{"flag":"paymentFailure","variant":"50%"}'
  1. 00aryan-2255/SRE_agent is the team repo: NightShift, docs, plan. aryan-2255/opentelemetry-demo is the shop, linked into it as astronomy-shop/; the agents read its commits and open their PRs there.
  2. 01bootstrap.sh fills in paths, installs Python packages, and starts the shop and NightShift’s containers.
  3. 02TrueForge opens at localhost:8790. Models, sandbox, GitHub and Jira are set once in its Settings.
  4. 03The dashboard opens at localhost:8090. The watcher starts at once.
  5. 04Flip a failure switch and the incident appears within a minute. Approve on the dashboard or on Jira.
